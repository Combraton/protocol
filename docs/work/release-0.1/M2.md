## Design outline (normative text goes into CORE.md)

### Grants

- **Record.** A grant is a provider-owned subject of kind `core.grant`. It holds: holder principal, audience (the provider's configured ID), rights (operation-family right names such as `core-test.read`), resource scope (subject kinds with an exact ID or an ID prefix), optional expiry (RFC 3339 UTC, provider clock), optional authority-epoch binding, delegation bounds (`allowed`, `max_depth`) and optional parent grant.
- **Root authority.** Principals named as authorities in the provider's launch configuration hold implicit authority. This is the standalone caller authority from ADR 001. Everyone else names a grant in the new envelope field `grant`, part of the negotiated feature `core.grants`.
- **Delegation.** A delegated grant cannot exceed its parent in rights, scope, expiry or depth. Revoking a grant revokes its descendants.
- **Check order.** Authorization is step 6, after deduplication. A principal may replay the stored result of its own already-bound command after revocation, because a replay performs no new mediated operation. Every new command or query needs a valid grant.
- **Non-leakage.** An operation outside the principal's grants gets `permission_denied`, whether or not the subject exists. A grant ID not held by the principal is reported like a nonexistent one. Deduplication keys are scoped by principal.

### Events

- **Recording.** Every accepted command appends at least one event in the same owner transaction. An event holds stream ID, stream epoch, sequence, subject, owner revision, recorded time (metadata only), causing `operation_ref` and command ID, event type and normalized payload.
- **Cursors.** Cursors are opaque strings. A cursor from another stream or an unknown epoch gets `invalid_cursor`.
- **Retention gaps.** A cursor older than retention returns `gap: retention` with a snapshot of the filtered subjects at a stated sequence. It never returns a silently partial replay.
- **Epoch changes.** A stream-epoch change, such as a restore from backup, is reported explicitly with the last sequence the provider can vouch for.
- **Subscriptions.** Notifications carry the same event objects. Reconnecting may replay events; consumers deduplicate by stream, epoch and sequence.

### Capabilities

- **Snapshot.** `core.capabilities` returns a revisioned snapshot: per-profile features, limits and capability predicates. Each predicate has status (`supported`, `unsupported` or `unknown`), enforcement level where relevant, and evidence.
- **Loss.** A capability that becomes unavailable (in tests, through launch configuration) refuses new dependent commands with `capability_unavailable` and raises the snapshot revision. Commands bound earlier replay unchanged.

### Unix-socket principal credential (U12 — recommendation for the owner)

**Recommendation:**
- The provider issues a random 256-bit bearer credential per principal, stored in a `0600` file inside a provider-owned `0700` directory. It can also be handed to a launcher through an inherited descriptor.
- The caller presents it in a new pre-negotiation operation, `core.authenticate`. The provider compares in constant time, never logs it, and supports revocation and rotation.
- The same-user peer check stays mandatory.

**Honest limit:** any process running as the same operating-system user can read a credential file unless something stops it. Credentials therefore distinguish principals only when agent processes are sandboxed away from the credential directory, or run as another user. PIO must keep credential paths outside agent-readable scope where it can enforce that, and report cooperative-only protection where it cannot. Credentials are never placed in agent environments or command lines.

**Alternatives:**
- Public-key challenge-response gains nothing locally, because the private key file has the same exposure.
- Separate OS users per principal give real separation but are heavy for standalone users.
- A same-user check alone cannot tell an agent from its supervisor.
