# M3 task — Execution profile (draft task packet)

- **Status:** draft plan, written during M2 on 2026-09-13. Refine before implementation starts; nothing here is normative yet.
- **Start condition (owner, 2026-09-13):** M3 starts only after the owner accepts M2 ([PR #3](https://github.com/Combraton/protocol/pull/3)). It is delivered in a separate PR.
- **Tracking:** [issue #1](https://github.com/Combraton/protocol/issues/1). Plan: [PLAN §5 M3](PLAN.md#m3--execution-profile).
- **Sources:** pio `docs/spec/SPEC.md`, `docs/spec/INTERNALS.md` and `docs/spec/STANDALONE-CLIENT.md` at `e65b7c0`; protocol SPEC §5–§6, §8, §12–§14; matrix rows EXE-1 to EXE-23, EFF-1 to EFF-4, OBS-7, TRN-4, SCN-2, SCN-3, SCN-10.

## Outcome

An `execution/1` profile that any executor can implement — PIO or a third-party minimal executor — and any caller can rely on. It must cover execution identity, the separate status axes, delivery proof, completion receipts, cancellation, steering, reconciliation, controller leases, workspace leases, usage and liability, and context binding.

Conformance must distinguish honest from optimistic executors. A deterministic reference executor drives a scripted fake harness. The fixtures inject delivery ambiguity, crashes between journal and dispatch, late old-attempt results and lost acknowledgments. Real-harness adapter evidence belongs to PIO's own gate, not to this profile's fixtures.

## Proposed shape (to be decided in the task)

### Subjects and identities (EXE-1)

- An **execution** subject is created by `execution.submit`.
- A **retry** is a new execution with `predecessor` set.
- Envelope `correlation` carries caller correlation opaquely (EXE-20).
- Invocation, delivery, completion and native-session identities are separate fields.

### Axes (EXE-2 to EXE-5)

| Axis | Values |
|---|---|
| `admission` | `queued`, `admitted`, `refused` (with reason) |
| `delivery` | `pending`, `acknowledged`, `failed_before_delivery`, `ambiguous`, each with a proof class: `provider_ack_id`, `echo`, `transport_only`, `bytes_written` |
| `runtime` | `preparing`, `active`, `requires_action`, `quiescent`, `exited`, `unknown` |
| `result` | `absent`, `partial`, `returned` |
| `exit` | exit status or `unavailable` |
| `evaluation` | external reference or `not_requested`, never derived from `exit` |

Each axis changes only through an event carrying its evidence class. A later reconciliation appends events; it never rewrites ambiguity.

### Operations

| Operation | Returns |
|---|---|
| `execution.submit` | Execution reference and admission |
| `execution.inspect` | Current axes plus a cursor |
| `execution.cancel` | Request receipt only (EXE-8) |
| `execution.steer` | Request receipt or explicit `unsupported` (EXE-9) |
| `execution.respond_action` | Response to a native action request, scoped to its execution (EXE-14) |
| `execution.reconcile` | Scoped observations for a command or delivery ID; never resubmits (EXE-10) |
| `execution.controller.claim` | Controller lease with epoch; stale controllers refused; observers unaffected (EXE-13) |
| `execution.workspace.checkpoint` | Coverage-declared checkpoint (EXE-15) |

Watch uses the Core event stream with `kinds: ["execution"]` (EXE-7).

### Completion receipts (EXE-6)

- A receipt is immutable and bound to execution, invocation, host generation, claim token, output descriptors and capture coverage.
- A matching duplicate returns the same receipt; conflicting content is refused.
- A receipt from an old attempt is retained but cannot finalize its successor.

### Capabilities (EXE-11, EXE-12)

Adapter capability predicates reuse Core §17, adding adapter, harness and protocol versions, probe time, limits and enforcement level. Harness discovery facts are an optional feature. A required restriction above the advertised enforcement level is refused at admission (EXE-2).

### Usage and liability (EXE-16, EXE-19)

- Usage has a basis: `observed`, `estimated`, `unknown` or `enforced_bound`.
- A timeout keeps unresolved liability; it is never a refund.
- A hard ceiling that cannot be enforced is refused.
- Queue, delivery, execution, inactivity and reconciliation timeouts are distinct.

### Context binding (EXE-17, EXE-18)

- A submit carries packet bindings, each with digest, obligation kind and boundary.
- Required-before-start without a satisfied binding is not admitted as ready.
- Packet delivery observations include `late`, `unavailable` and `unknown`.

### Core effects (EFF-1 to EFF-4)

Effect descriptors and retry classes are defined in Core. Prompt submission, steering and cancellation delivery are the effects exercised. An effect's status can be `unknown` with an open obligation; a closed wait never proves non-occurrence.

### Telemetry and backpressure (OBS-7, TRN-4)

- Output chunks travel in a telemetry channel separate from semantic events, with explicit lost-range records.
- A slow subscriber is terminated with a typed error and resumes from its cursor. It never silently loses semantic events.

## Conformance approach

- **Reference executor.** An `execution` implementation in the reference provider drives a scripted fake harness. Launch configuration selects its behavior: acknowledge, echo only, PTY bytes only, crash after write, never exit, return late, refuse cancellation, emit an action request, exceed an output spool. The fake harness is test environment only.
- **Negative fixtures.** Each carries mutants in the style of M1/M2, for example:
  - labels bytes-written as acknowledged;
  - reruns on lost acknowledgment;
  - reports cancelled on request;
  - last completion wins;
  - evaluation from exit;
  - refunds liability on timeout;
  - shares action IDs across executions;
  - accepts a stale controller;
  - drops telemetry silently.
- **Scenarios.** Fault-injection scenarios SCN-2, SCN-3 and SCN-10.
- **Runner additions.** A pipelined-request step (responses in any order), an event-ordering property check, and launch-configuration controls for the fake harness.
- **Independent implementation.** The independent implementation is extended to `execution/1` by a spec-only helper.

## Open questions for the task (decide with evidence; escalate public-semantics changes)

1. Is `execution.watch` a separate operation, or Core subscriptions with an execution kind? The draft proposes Core subscriptions.
2. How is output content exposed: Evidence descriptors (M4) or an execution-local spool read? A spool with evidence export later is proposed.
3. Are workspace leases and checkpoints in `execution/1` or an optional feature? An optional feature is proposed, since read-only executors may not need them.
4. Which enforcement vocabulary is shared with Core §17: the same three levels, or a richer set?
5. What is the minimum a third-party minimal executor must implement: submit, inspect, cancel (receipt), reconcile and receipts, with steering, actions and workspaces as features?

## Acceptance

The owner directed on 2026-09-13 that these stay explicit acceptance criteria. None may be dropped silently. If one cannot be met, it is escalated with evidence and recorded as deferred.

1. **Effects and reconciliation (EFF-1 to EFF-4).**
   - Core defines effect descriptors and retry classes.
   - An effect's status can be `unknown` with an open obligation; a closed wait never proves non-occurrence.
   - `execution.reconcile` returns scoped observations and never resubmits.
   - Each row has positive and negative fixtures with killing mutants, for example "reruns on lost acknowledgment" and "reports cancelled on request".
2. **Telemetry lost ranges (OBS-7).** Output travels in a telemetry channel separate from semantic events, with explicit lost-range records. A mutant that drops telemetry silently is killed.
3. **Backpressure (TRN-4).**
   - A slow subscriber is terminated with a typed error and resumes from its cursor.
   - Semantic events are never lost silently, and telemetry coalescing is declared.
   - Fixtures cover a slow consumer on both bindings.
4. **Fault injection.**
   - Deterministic injected faults: delivery ambiguity, a crash between journal and dispatch, lost acknowledgments, late old-attempt results.
   - The `unavailable` and `internal_error` "nothing bound" and "outcome unknown" semantics carried over from M2.
   - SCN-2, SCN-3 and SCN-10 pass on the reference executor over both bindings.
5. **Scripted test executor.**
   - Conformance uses a deterministic reference executor that drives a scripted fake harness selected by launch configuration. The script is test environment, not protocol.
   - A real harness adapter is PIO work: its evidence belongs to PIO's own gate, and no M3 fixture depends on a real harness.
6. **Execution rows.** Every EXE row in scope has positive and negative fixtures with killing mutants.
7. **Test clock.**
   - Launch configuration gains a controllable clock, so timeouts and idle grant expiry during a session become observable.
   - This closes the M2 close-out follow-up on idle expiry.
8. **Independent evidence.** A spec-only helper extends the independent implementation to `execution/1`. It passes, or its divergences are resolved as in M2.
9. **CI.** CI is green, with result manifests, transcripts and mutant summaries uploaded for every job, and outcomes kept distinct (`pass`, `fail`, `timeout`, `harness_error`, `unsupported`, `skipped`).
