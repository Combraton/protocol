## Outcome

Two profiles any provider can implement, and callers and executors can rely on:
- `evidence/1`: exact artifact identity, staged upload and seal, provenance and coverage, authorized query and fetch, manifests, availability and retention with proof-loss reports, and work bindings;
- `context/1`: requests with basis, obligations, reliance and limits; shared jobs with separate subscriber cancellation; exact packets with citations, labels, coverage and gaps; updates, corrections and stale-basis detection; and behavior when the provider is unavailable.

Conformance must distinguish honest from optimistic providers with **reference participants only**: a reference evidence provider with a scripted store, a reference context provider with scripted preparation, and the M3 reference executor. **M4 does not implement the real CBR memory engine or PIO adapters**; their evidence belongs to their own gates.

## Questions for the owner

These change the contract or the conformance architecture, so they are brought to the owner before step 2. Each has a recommendation.

| # | Question | Recommendation |
|---|---|---|
| M4-Q1 | **Byte transfer for 0.1.** In-band bounded chunks over the stream binding, or out-of-band locators? | In-band bounded chunks (`append`, ranged `fetch`). Out-of-band transfer and signed URLs wait for Remote trust; locators stay informative. |
| M4-Q2 | **Packets as Evidence artifacts.** Should every packet revision be a sealed Evidence artifact (so Context depends on Evidence), or a Context-owned object? | Evidence artifacts: exact identity, retention, holds, purge reports and fetch are defined once. A context provider without a separate evidence service implements `evidence/1` for its own packets. |
| M4-Q3 | **Cross-profile topology in conformance.** The runner drives one participant today. Scenarios need a caller, an executor and a context provider, and the executor fetches packets and publishes evidence. | Runner-orchestrated multi-participant cases: the runner starts separate reference participants, and the reference executor reaches the reference context and evidence providers as an ordinary protocol client over the Unix socket, named in launch configuration. In-process composition inside one reference binary would not exercise the protocol boundary. |
| M4-Q4 | **Stale-basis revalidation.** Who revalidates packet applicability at admission? | The executor checks the invalidation conditions it can observe against the basis it holds, adding a `stale` binding state to EXECUTION §13. The caller's own revalidation stays the caller's. This extends the accepted Execution profile. |
| M4-Q5 | **New error codes.** Evidence needs `upload_incomplete`, `content_digest_mismatch`, `digest_not_current` and `hold_active`; Context refusals use outcomes (`refused` with `budget_insufficient`). | Add the four codes to the Core registry, with retry classes `same_command` for `upload_incomplete` and `no` for the others, rather than overloading `precondition_failed`. |
| M4-Q6 | **Purge with holds.** Should purge override holds when it names them, or always be refused while holds exist? | Refuse by default (`hold_active`); allow an authorized purge that names the holds it releases, and list them in the proof-loss report. |
| M4-Q7 | **Manifest format.** A minimal protocol media type, or in-toto Statements now? | Minimal manifest media type now; in-toto export shape in M5/M6 with Verification, as SPEC §10 suggests. |

## Acceptance

None may be dropped silently. If one cannot be met, it is escalated with evidence and recorded as deferred.

1. **EXE-21 is explicit.** Execution outcomes reference sealed artifacts by artifact and exact digest; references resolve only through authorized Evidence operations; mutants for unsealed or mismatched references are killed.
2. **Exact artifact and packet identity.** References carry digests; fetched bytes equal the sealed bytes; locators are never identity; regenerated or relabeled bytes are detected.
3. **Authorized access.** No existence leaks in inspect, query, fetch or expand; packet-bound read grants cover only their packet and audience.
4. **Provenance and availability.** Producer bound to the session principal; required coverage; availability states; purge with proof-loss report; integrity failure never serves bytes.
5. **Missing required context.** Unmet at deadline, never satisfied or downgraded; advisory follows its declared fallback; bound work is not admitted as ready.
6. **Corrections during preparation.** An older derivation never becomes current for a corrected binding item.
7. **Stale basis.** Detected before admission; work bound to a stale packet is not admitted as ready.
8. **Shared-subscriber cancellation.** Cancelling one request never cancels a job other requests need.
9. **CBR outage.** Advisory proceeds with a visible gap; required waits at its named boundary; no fail-open.
10. **Preparation/resource dependency cycle.** A consumer waiting for context holds no execution reservation; job-initiated executions carry their origin and are not re-enriched.
11. **Reference participants only.** No fixture depends on the real CBR memory engine or on PIO adapters; scripted providers are test environment, never protocol.
12. **Independent evidence.** The independent implementation passes the fixtures for what it claims, or its divergences are resolved.
13. **CI.** Green, with manifests, transcripts and mutant summaries uploaded and outcomes kept distinct; coverage limits are recorded, never counted as passes.
