## Outcome

Two profiles that any provider can implement and any reader can check:
- `knowledge/1`: claims with immutable revisions and lineage, three semantic planes, support with declared lineage, conflict and drift records, applicability evaluations against a target basis, reliance decisions under one explicit authority binding per scope, and history.
- `verification/1`: exact contracts, `evaluate_contract` job references, immutable receipts with per-property results, and an assessment in which missing, unavailable or outdated verification is never a pass.

Two cross-profile additions: packets that carry claims, and a provider that reconnects with a changed capability.

Conformance again uses **reference participants only**: a reference knowledge provider, a reference verifier with a scripted evaluator, and the M4 context, evidence and execution references. **M5 does not build the real CBR memory engine or PIO adapters**, and it does not implement Coordination gates.

## What M5 will establish, and what it will not

**Establishes**, once accepted with fixtures, mutants and independent evidence:
- Evidence, claims and authority decisions are separate records with separate identities; no claim or receipt records a decision.
- A claim revision never changes. Revisions, corrections, supersession and conflicts are later records, and history keeps all of them.
- Reliance, applicability, subject health and evidence availability are reported as four facets, each naming its source.
- Repetition through shared lineage never raises support.
- Only the one bound authority for a scope decides reliance or resolves conflicts. Producers, derivations, grants and verifiers do not.
- A receipt names exact subjects, contract, evaluator, environment and a result for every contract property.
- An assessment treats not evaluated, indeterminate, mismatched, stale and unavailable as not satisfied.
- A packet carrying claims keeps their exact revisions, reliance and applicability, and cannot promote a claim through a label.
- Work pinned to a capability keeps its meaning when a provider reconnects with that capability changed.

**Does not establish:**
- that any claim is true, that multiple lineages are truly independent, or that an evaluator is correct;
- memory quality, retrieval quality or context usefulness; those belong to CBR's own evaluation plans;
- project acceptance or gate evaluation; Coordination is unsupported in 0.1, and the local authority binding is the standalone mode;
- signed receipts or offline verification; they are deferred with Remote trust (U2);
- mixed-implementation composition; M5 compositions still run one implementation for every participant (see [carried-forward coverage](#m4-coverage-carried-forward)).

## Intended behavior in examples

These examples show the proposed semantics before any implementation. Identifiers are illustrative.

**1. Drift is not a contradiction (KNW-2).**
- Scope `svc`, subject `{ kind: "service", id: "billing" }`, predicate `queue`.
- Revision A, plane `normative`, value `"v2"`: the architecture decision. It is `accepted_for_use` for `binding` use.
- Revision B, plane `observed`, value `"v1"`, support: a runtime trace at tree `t9`.
- `conflict.open` on A and B records **drift**. Both revisions keep their content and facets. Nothing is deleted or demoted, and no winner is chosen. A packet can carry A as `binding` and B as `runtime_observed`, together with the drift.

**2. Shared lineage is not corroboration (KNW-4).**
- Three agent summaries each propose "the auth flow is correct", all supported by the same model derivation record `d1`. Every entry has root `{ kind: "derivation", record: d1 }`, so support is `single_lineage`, however many times it repeats.
- Adding support from a CI test report captured separately, root `{ kind: "evidence", digest: sha256:… }`, gives `multiple_lineages`. That still says only that the declared lineages do not overlap.

**3. A model cannot pick a winner (KNW-5).**
- Two `interpretive` revisions disagree on a retry limit.
- The CBR maintenance principal opens the conflict and attaches a suggested discriminating test. It then calls `conflict.resolve` with `select`, which is `permission_denied` with `not_authority`.
- A newer revision from the same producer does not resolve the conflict either. The bound authority resolves it with `narrow_scope`, and both values stay in history.

**4. Four facets at once (KNW-3).**

```json
{ "reference": { "claim": "parser-handles-bom", "revision": 2, "digest": "sha256:…" },
  "reliance": { "state": "accepted_for_use", "permitted_use": "evidence", "decision": "dec-7" },
  "applicability": [ { "evaluation": "ev-3", "target": { "repositories": [ { "id": "repo-a", "tree": "t12" } ] }, "result": "invalid_for_target" } ],
  "health": "not_applicable",
  "availability": "purged" }
```

The claim was accepted at tree `t10`. At `t12` the file its condition names changed, and its supporting test log was purged under retention. None of these facts rewrites the others.

**5. An extracted instruction stays a proposal (KNW-9).**
- A model extracts "always run migrations before tests" from a transcript as a `normative` claim. It is `proposed`.
- A packet can carry it only as a `hypothesis` or `inferred` section. A `binding` item it would satisfy stays `unmet` with reason `not_accepted`.
- Once the bound authority records `accepted_for_use` with `permitted_use: binding`, a later packet may label it `binding`. The earlier packet is unchanged.

**6. Unavailable checks are not passes (VER-1, VER-4).**
- Contract `c1` has required properties `parser.unit` (component) and `upload.journey` (journey).
- The receipt reports `parser.unit: pass` and `upload.journey: indeterminate`, reason `browser_unavailable`.
- `assess` gives `parser.unit: satisfied`, `upload.journey: not_satisfied (indeterminate)`, and `overall: not_satisfied`. A receipt that omitted `upload.journey` is refused when recorded.

**7. Outdated verification is not a pass (VER-4).** The same receipt, assessed:
- for subject tree `t13` while the receipt verified `t12`, gives `subject_mismatch`;
- after `validity.valid_until`, or past the contract's freshness window, gives `stale`;
- against contract revision `c2`, gives `contract_mismatch`.

Each of these is `not_satisfied`, even for properties that passed.

**8. A failing receipt is not a stop command, and a passing one is not acceptance (VER-2, VER-5).**
- A receipt reports `fail` for a property of execution `e-5`'s output. `e-5` keeps every axis, and its running work continues.
- A fully satisfied receipt for claim `parser-handles-bom` leaves its reliance `proposed`. The verifier's own `decision.record` is `not_authority`. The bound authority may accept the claim and cite the receipt in `validation_basis`.

**9. Reconnect with a changed capability (SCN-7).**
- Verifier `v` advertises `verification.evaluator.journey` at version `1`, with job `j1` admitted and pinned to version 1.
- `v` restarts advertising version `2`. The caller reconnects, renegotiates and reads `core.capabilities.changed`.
- `j1` finishes under version 1, or, if version 1 is no longer available, completes with its unevaluated properties `indeterminate` (`evaluator_unavailable`).
- A new job `j2` pins version 2. Receipts issued earlier still name version 1.
- If `v` restarts with the evaluator `unsupported`, new jobs are `capability_unavailable`, and nothing already recorded changes.

**10. A packet carrying claims (KNW-10, SCN-16).**
- A context request asks for three items. The packet (`combraton-context-packet/2`) carries:
  - claim `A@1`, accepted for `binding`, as a `binding` section;
  - claim `B@3`, proposed and interpretive, as an `inferred` section;
  - claim `C@2`, whose evaluation for the packet basis is `invalid_for_target`, as a `stale` historical section.
- After publication the authority rejects `A@1`. The packet bytes are unchanged, and `context.packet.inspect` now reports `claim_changes: [ { section_id: "s-a", claim: A@1, change: "reliance_changed" } ]`.

## Reuse and compatibility

M5 reuses the accepted contracts and adds nothing to them silently.

| Contract | Reused as is | Change proposed |
|---|---|---|
| Core | Command path and idempotency; grants and `constraints`; authority epochs (§8) for authority bindings; events; capability snapshots (§17) for evaluators; existence rules | **Additive.** CORE §12 gains codes `authority_scope_bound` and `claims_not_comparable` (M5-Q3, M5-Q1). `permission_denied` gains reason `self_decision`. |
| Evidence | Exact references, sealed artifacts, fetch, availability and purge, work bindings | None. Contracts and receipts are new artifact formats (`combraton-verification-contract/1`, `combraton-verification-receipt/1`), not new Evidence semantics (M5-Q5). |
| Context | Requests, items, labels, packets, conditions (reused by claim `conditions`) | **Negotiated extension.** Feature `context.claims`, packet format `combraton-context-packet/2` and `claim_changes` at inspect (M5-Q7, CMP-9). Sessions without the feature see M4 behavior. |
| Execution | Status axes; `evaluation` stays an attributed external reference; context revalidation | None required. **Candidate:** `packet.facts` reports `mismatch` when a claim carried for a required item loses its binding acceptance (M5-Q7). |

## Provider and consumer assumptions, with counterexamples

| Assumption | Counterexample the contract must survive |
|---|---|
| A reader can tell which revision a statement came from | A packet cites "latest": after revise, the same citation means different content. Hence exact revision references with digests. |
| An authority is identifiable per scope | Two standalone tools both configured to accept for `svc`. Hence one binding per scope, transfer by epoch. |
| Producers are distinguishable from deciders | The model runtime principal also holds broad grants. Hence deciding needs the binding, not a right, and never the producer (M5-Q3). |
| Support can be compared | The same derivation summarized three times. Hence declared lineage roots, and no "independent" wording. |
| Applicability is decided against a target | An accepted claim silently assumed valid on a new branch. Hence evaluations need a target, and missing coverage is never applicable. |
| A receipt is about exact subjects | A passing receipt for tree `t12` reused for the integration tree `t13`. Hence subject digests in every assessment. |
| Unavailable is not a failure and not a pass | A browser outage recorded as `fail` stops unrelated work, or recorded as `pass` hides a missing journey. Hence `indeterminate` with a reason, `not_satisfied` at assessment, and no stop semantics. |
| Capability meaning is pinned | The evaluator is upgraded mid-job, and old receipts appear to have used the new version. Hence pinned evaluator identity in jobs, receipts and evaluations. |
| Readers verify what they fetch | A knowledge or receipt holder serves content whose digest does not match the reference. Hence readers check digests, as the M4 executor checks packet bytes. |

## Proposed decisions

Each question has a recommendation and alternatives. Implementation of the affected semantics waits for the owner's decision. Routine work continues meanwhile: schema scaffolding for undisputed identities, and runner support.

**M5-Q1. Claim content shape.**
- **Recommendation:** a structured `statement` `{ subject, predicate, value }`, with optional prose as an Evidence reference; `plane` one of `normative`, `observed`, `interpretive`; comparable claims share subject, predicate and scope `id`, and otherwise `claims_not_comparable`.
- **Alternatives:**
  - prose-only claims with optional structured slots, where comparability is declared by the producer;
  - free-form predicates without scope ids.

  Both make conflict and drift checks unverifiable by a black-box fixture.

**M5-Q2. Support lineage and support class.**
- **Recommendation:** declared lineage roots (evidence digest, claim lineage, derivation record), with classes `unsupported`, `single_lineage` and `multiple_lineages`; never the word "independent".
- **Alternatives:**
  - provider-defined independence policies advertised as capabilities, which are richer but provider-specific and untestable across providers;
  - no class, only the raw roots, which is simpler but leaves KNW-4 to every reader.

**M5-Q3. Authority, delegation and self-decision.**
- **Recommendation:**
  - one binding per scope `id`, with exact scope equality in 0.1;
  - a transfer raises the Core authority epoch; earlier decisions stay in effect until the new authority decides otherwise;
  - only the bound authority principal decides, and a grant never makes one;
  - no delegation of deciding in 0.1;
  - the producer of a revision never decides it (`self_decision`).
- **Alternatives:**
  - hierarchical scopes where a parent binding covers children, which is more expressive but needs overlap rules and fixtures;
  - delegated deciding through a typed grant constraint `knowledge.authority` bound to the epoch;
  - a transfer that returns every revision in the scope to `proposed`, which is safer after a disputed takeover but discards standing acceptances;
  - allowing a human authority to accept its own `human`-derivation statements, flagged `self_stated`. This fits standalone single-user use, but weakens the "producers cannot self-accept" row; the recommended alternative is to publish under a separate producer principal.

**M5-Q4. Applicability results.**
- **Recommendation:**
  - evaluations over typed conditions (reusing Context kinds) and declared dependencies, with evaluator `{ id, version }` pinned;
  - `applicable` only with complete coverage;
  - `invalid_for_target` only on an observed mismatch;
  - `needs_check` when anchors exist but something could not be checked;
  - `unknown` when anchors or evaluator support are missing;
  - cycles are `needs_check`.
- **Alternatives:**
  - merge `needs_check` and `unknown`, which is simpler but loses the "you can resolve this by checking" signal CBR §5 relies on;
  - allow provider-specific result extensions.

**M5-Q5. Identity of contracts and receipts.**
- **Recommendation:** contracts and receipts are sealed Evidence artifacts in versioned formats, as packets are (M4-Q2), so identity, integrity, retention and fetch are reused; receipts are also `verification.receipt` subjects for jobs, events and query.
- **Alternatives:**
  - receipts only as verification subjects with a canonical digest, which is lighter but duplicates retention and fetch semantics;
  - in-toto Statement format now, which the release plan defers (§3.3).

**M5-Q6. Where the no-pass rules live.**
- **Recommendation:** normative rules in VERIFICATION §7, exposed as the read-only query `verification.receipt.assess` at any receipt holder, so fixtures can check them black-box; the result is an assessment, never an acceptance.
- **Alternatives:**
  - consumer-side rules only, which conformance cannot check;
  - a Knowledge "eligibility" projection on claims, which is closer to CBR's full-profile role but couples Verification to Knowledge, and a CI publisher would then need Knowledge.

**M5-Q7. Claims in packets and Execution impact.**
- **Recommendation:** Context feature `context.claims`, packet format `/2` with section claim snapshots and read-time `claim_changes`; labels cannot promote claims; Execution unchanged in 0.1, with consumers reading `claim_changes`.
- **Alternatives:**
  - also extend `packet.facts` so a required item whose carried claim loses binding acceptance reports `mismatch`. This is stronger protection at dispatch, but it is a further negotiated change to the accepted Execution extension.
  - carry claim references only, without snapshots, which leaves packets unable to show what the consumer was told.

**M5-Q8. History depth.**
- **Recommendation:** `knowledge.claim.history` returns every record in recorded order with stream positions. "As known at position P" and "now known about interval I" are named as distinct candidates and deferred past 0.1.
- **Alternatives:**
  - implement both reconstructions now, which CBR's temporal requirements favor, but would roughly double the Knowledge fixture work;
  - recorded order only, without naming the distinction.

**M5-Q9. Capability change for pinned work.**
- **Recommendation:**
  - evaluator capabilities are Core predicates `verification.evaluator.<id>` whose evidence names the version;
  - jobs and knowledge evaluations pin `{ id, version }`;
  - a lost evaluator ends a running job with `indeterminate` (`evaluator_unavailable`), never `pass` or `fail`;
  - new jobs follow the current snapshot;
  - nothing recorded is rewritten.
- **Alternatives:**
  - jobs wait for the evaluator to return, which is simple but can hang without bound;
  - lost evaluators mark jobs `failed`, which confuses unavailability with a property failure.

## Acceptance

None may be dropped silently. If one cannot be met, it is escalated with evidence and recorded as deferred.

1. **Separate records.** Evidence, claim revisions, decisions, evaluations, conflicts and receipts have separate identities. No operation on one records another implicitly.
2. **Revisions and lineage.** Immutable revisions with base checks; corrections, supersession and conflicts are later records; history retains everything.
3. **Independent facets.** Reliance, applicability, health and availability coexist in any combination, each with its source.
4. **No false corroboration.** Shared lineage never raises support.
5. **Authority.** Only the bound authority decides or resolves; producers, derivations, grants and verifiers are refused with their distinct reasons.
6. **Applicability.** Incomplete coverage never yields `applicable`; unavailable inputs never compare equal.
7. **Complete receipts.** Exact subjects, contract, evaluator and environment, and a result for every contract property.
8. **No pass by absence.** Not evaluated, indeterminate, mismatched, stale and unavailable are never assessed as satisfied.
9. **Scoped observations.** A failing receipt changes no execution state; a passing receipt grants no authority.
10. **Packets carrying claims.** Exact revisions, reliance and applicability travel; labels cannot promote; later changes are visible without rewriting packets; the extension is negotiated.
11. **Pinned capability meaning.** A provider reconnecting with a changed evaluator neither rewrites recorded work nor reports pass after loss.
12. **Reference participants only**, with coverage limits recorded and same-implementation compositions never described as mixed-implementation proof.
13. **Independent evidence** for what the independent implementation claims, with divergences resolved.
14. **CI** green with manifests, transcripts and mutant summaries, and outcomes kept distinct.
