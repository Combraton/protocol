## CMP-5 proposal — machine-readable feature dependencies (M6-Q1)

**Constraint discovered in the accepted contracts:** decision 002 makes every
envelope object closed (`unevaluatedProperties: false`; an unknown member is
`invalid_envelope`), and `core.describe` §4.1 advertises `features` as an
array of feature-name strings. Therefore neither adding a member to the
describe result (option C) nor turning `features` entries into objects
(option B) is additive: both would make a new provider's describe response
invalid to every existing client, before negotiation can even happen.

| Option | Mechanism | Older-client impact | Verdict |
|---|---|---|---|
| A | New pre-negotiation query `core.feature_dependencies` | None: a client that never calls it sees byte-identical behavior | **Recommended** |
| B | `features` entries become `{ name, requires }` objects | Breaks schema validation of describe for every old client; needs core major 2 | Reject |
| C | New optional member on the describe result | `invalid_envelope` under closed objects for every old client | Reject |
| D | Status quo: dependencies in profile documents; negotiation enforces with `dependency_not_selected` | None | Fallback if the owner wants no new surface in 0.1 |

**Option A in detail.**
- `core.feature_dependencies` (query, no params beyond the envelope) returns
  `{ "dependencies": [ { "profile", "major", "feature", "requires": [ { "profile", "features": [ … ] } ] } ] }`
  — exactly the dependencies negotiation already enforces, nothing more.
- CORE §4 and §10 add it to the pre-negotiation allowlist next to
  `core.describe` (socket sessions still authenticate first, §18).
- **Older client:** never calls it; describe, negotiate and every fixture
  from M0–M5 are unchanged. Fixture: existing negotiation fixtures re-run
  unmodified at the RC head (A1 covers this).
- **Newer client against an older provider:** receives `method_not_found`
  (the operation is unknown there) and falls back to the documents, exactly
  as today. Fixture: run the query against the M5-level independent provider
  before it is extended; assert `method_not_found` and an unchanged
  subsequent negotiation.
- **Consistency:** a fixture asserts the advertisement equals what
  negotiation enforces: requesting a feature without its advertised
  dependency still yields the accepted `dependency_not_selected` item.
- Enforcement authority stays with negotiation; the query is advisory
  planning data. Knowledge and Verification publish their Core dependencies
  through the same mechanism.

**Recommendation:** adopt A. It is the only additive machine-readable route
under the closed-object rule, its old-side behavior is provable with the
implementations already in the repo, and it removes the last
document-only dependency surface before consumers pin 0.1.

## Mixed-implementation composition (M6-Q2)

The carried gap: every M4/M5 composition runs one implementation for every
participant, and the independent Python provider serves stdio only. Mixed
interoperability does not require completing every feature of a second
provider; it requires the *boundaries consumers will actually cross* to be
exercised by two implementations over the public protocol.

**Smallest honest topology.** The third-party examples (A3) act as clients —
the client side of the Unix-socket binding needs no serving loop or
backpressure implementation:

- **S-A — third-party executor against reference providers.** The minimal
  executor (new code, contracts-only) connects over the Unix socket
  (credential file + `core.authenticate`, U12) to the reference context,
  knowledge and evidence providers. Scenarios: negotiate `execution` with
  `context.claims` at the context provider; bind a packet
  `required_before_start`; observe claim invalidation block the required
  boundary while advisory work proceeds (the SCN-16 shape); fetch and
  digest-check evidence bytes. This puts a second implementation on the
  consumer side of CMP-9's Execution half and the §13.1/§13.3 boundary.
- **S-B — third-party evidence publisher feeding reference consumers.** The
  minimal publisher seals a contract artifact and a subject artifact in the
  reference evidence store over the public protocol; the reference verifier
  then evaluates that contract and the assessment is read back. A second
  implementation produces what the reference consumes.
- **S-C (bounded extension, only if S-A/S-B land early):** the independent
  Python provider gains minimal Unix-socket *serving* (accept + framing +
  U12 authentication; no backpressure), letting one existing composition
  fixture run with the knowledge provider role played by the independent
  implementation against the reference executor.

**Remains untested and is recorded as such in the release record:** a
second implementation in the serving role for compositions (unless S-C
lands); backpressure and fairness across implementations; the barrier- and
signal-synchronized fixtures for non-reference participants; wording drift
of `observed` strings outside the S-A path; every real-adapter behavior
(PIO's gate, accepted scope limit).

**Recommendation:** commit to S-A and S-B for the RC; treat S-C as
opportunistic. This is the smallest topology that makes "mixed
implementation" an honest sentence for the boundaries 0.1 consumers cross
first.

## Carried-forward gaps: release disposition (M6-Q3)

Dispositions are proposals until the owner confirms. "Closed" means fixture
plus mutant evidence at the RC head. A closure that would *change* reference
behavior (not merely guard it) first gets a compatibility assessment and, if
it alters accepted semantics, an old-client fixture — stricter validation is
not treated as additive merely because it is within an accepted milestone's
scope. The M5 contract-shape readings and the scripted-`unmet` resolution
stay recorded in [M5-DIVERGENCES](M5-DIVERGENCES.md) and the spec; nothing
in M6 supersedes them silently.

**Required before release (the consequential four):**

| Gap | Why consequential | Closure |
|---|---|---|
| `decision.record` without `knowledge.read` on its claim (unguarded authority path) | An authority check that only the reference enforces is exactly the class of divergence M2–M5 existed to prevent | Fixture + mutant on the specified right check; no behavior change expected (implemented and specified; currently unguarded) |
| Required-boundary enforcement checked on one implementation only (SCN-16, CMP-9 Execution side) | The claim boundary is 0.1's central safety promise to consumers | S-A topology above |
| Job loses its evaluator before its first evaluation (HM5B-QUEUED-LOSS) | "Never a pass by absence" is Verification's core rule; the queued-loss path is specified but unguarded | Fixture + mutant: unfinished properties `indeterminate`, receipt names the pinned version |
| Exact `max_age_seconds` boundary | Boundary instants are where independent implementations diverge silently; the `valid_until` boundary is guarded, the freshness one is not | Fixture at the exact boundary instant on both sides |

**Explicit accepted limitations (named in the release record):**
no fairness bound among released executions; all Execution evidence is
scripted (real adapters are PIO's gate); root is the only other OS user
tested; capability evidence-source and cursor-past-head checks are
reference-only; the independent provider serves stdio only (modulo S-C);
temporal reconstruction deferred (M5-Q8); no signing or offline receipt
verification (U2, Remote trust); Coordination unsupported; Windows
unsupported (U4); the mixed-implementation remainder listed under M6-Q2.

**Deferred work (backlog, not blockers, kept with their impact):**
Evidence edge cases (`evidence.availability.changed`, shrinking fetch
limits, sealed-but-unavailable manifest child, `released_holds` filtering,
rarer credential-locator forms); Context edge cases (script `end`/`unmet`
steps in Context's own flows, `omit` naming an item, `dirty_snapshot` and
`environment_digest` in Context's own conditions, cancel with no remaining
subscriber, job-event visibility, shared jobs with different fallbacks,
corrections on advisory items); revalidation timing edges (advisory checks
at dispatch, deadlines and inactivity due at release end); Knowledge:
`conflict.resolve` step-7 order fixture (decision path is guarded),
duplicate `condition_id`; Verification: rarer contract violations (unknown
layer, non-boolean `required`, empty lists); Context: `unverified_items`
beyond `binding`/`evidence` items, resolved conflicts left out of
snapshots.
