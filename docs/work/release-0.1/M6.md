## CMP-5: `core.feature_dependencies` (M6-Q1)

### Why a new query

Decision 002 makes every envelope object closed, and `core.describe` (§4.1) advertises `features` as an array of names. Adding a member to the describe result (option C), or turning `features` entries into objects (option B), would therefore make a new provider's describe response invalid for every existing client. A new query is the only additive route. Options B and C are rejected, and D (documents only) remains the fallback for providers that predate the query.

### What counts as a dependency

A dependency is listed exactly when **negotiation enforces it within one session**. Selecting the dependent item without the dependency either refuses the negotiation or leaves the dependent item unselected, with a `dependency_not_selected` item (CORE §4.2).

Not listed: a protocol dependency between separate providers. Context, Knowledge and Verification cite exact Evidence artifacts, but negotiating them does not require `evidence/1` in the same session. The reader negotiates `evidence/1` at the provider a reference names, which may be a different service (CONTEXT §1, KNOWLEDGE §1, VERIFICATION §1). A Context provider that uses an Evidence service is not a session dependency of `context/1`.

### Shape

`core.feature_dependencies` is a query in base `core/1`, not a feature, with an empty payload `{}`. Its result is `{ dependencies: [ entry ] }`. Each entry:

| Member | Meaning |
|---|---|
| `profile`, `major` | The dependent profile major; one the provider supports, as listed by `core.describe` |
| `trigger` | `{ kind: "profile" }`: the dependency applies whenever that profile major is selected. `{ kind: "feature", feature }`: it applies only when that feature of the profile is selected. |
| `requires` | A non-empty list of `{ profile, major, features }`. For each, that profile major must be selected in the same session, together with every listed feature. An empty `features` list means the profile major alone is required. |

The two trigger kinds keep a whole-profile dependency from posing as a feature, and the `requires` entries always name a profile major, even when the requirement is a single feature.

**Example: the reference provider in 0.1.**

```json
{ "dependencies": [
  { "profile": "execution", "major": 1, "trigger": { "kind": "profile" },
    "requires": [ { "profile": "core", "major": 1, "features": ["core.events", "core.capabilities", "core.effects"] } ] },
  { "profile": "execution", "major": 1, "trigger": { "kind": "feature", "feature": "execution.claim_revalidation" },
    "requires": [ { "profile": "execution", "major": 1, "features": ["execution.context_revalidation"] } ] },
  { "profile": "evidence", "major": 1, "trigger": { "kind": "profile" },
    "requires": [ { "profile": "core", "major": 1, "features": ["core.events"] } ] }
] }
```

`context/1`, `knowledge/1` and `verification/1` follow the evidence pattern with their Core features. `core-test/1` lists `core/1` with no features.

### Rules

- **Complete and ordered.** Every supported profile major other than `core` has one `profile` entry naming `core/1` and the Core features it requires, which may be none. `feature` entries follow for each feature with an enforced dependency. Entries are ordered by describe's profile order: the `profile` entry first, then `feature` entries in describe's feature order.
- **When it may be called.** It is allowed before negotiation, beside `core.describe` and `core.negotiate` (CORE §3, §10 step 1). The authentication rules are unchanged: on a shared transport it needs a successful `core.authenticate` first, like `core.negotiate` (CORE §18.2).
- **Read-only.** It creates no command record, appends no event and changes no session state. Calling it does not negotiate.
- **Bounded.** The result is determined by the provider's manifest. It lists only supported profile majors and their features, and it fits the default 1 MiB frame, since no receive limit has been negotiated yet.
- **Advisory.** Negotiation stays authoritative. A consumer still negotiates every dependency it relies on, and a provider enforces them whether or not the query was called.
- **Older providers.** An older provider answers `method_not_found`. The consumer then falls back to the requirements documented in the profile documents it pinned, and still requests them at negotiation. Fallback never means dropping or assuming a required feature.

### Enforcement finding: a documented feature dependency that was not enforced

- **The defect.** EXECUTION §13.3 says `execution.claim_revalidation` "requires `execution.context_revalidation`". Negotiation in the accepted reference does not enforce this: it selects `execution.claim_revalidation` alone. The query must describe only enforced dependencies, so advertising this one without enforcing it would be false.
- **Resolution.** CORE §4.2 gains the feature-triggered rule:
  - **Not selected.** A requested feature whose dependency is not selected is itself not selected. The item is `{ profile, feature: <the requested feature>, reason: "dependency_not_selected" }`.
  - **Refusal.** When that feature was required in a required profile, negotiation is refused with `unsupported_required_feature`. A profile-triggered `dependency_not_selected` still gives `unsupported_profile`.
  - **Optional profile.** When the feature was required in an optional profile, the profile is not selected.
  - **Optional feature.** When the feature was optional, it is reported in `unselected`.
- **Compatibility assessment.** Behavior changes only for a session that requests `execution.claim_revalidation` without `execution.context_revalidation`. Before the change that session got a selected feature it could not use: every claim-carrying binding needs the §13.1 binding members, which are `invalid_envelope` without `execution.context_revalidation`. Sessions requesting both, or neither, are unaffected. Running the accepted M5 fixture set unmodified against the new provider checks that no accepted fixture depended on the old behavior (A1).
- **Other combinations considered and not added.** Two feature combinations are usable only together in practice: `execution.context_revalidation` without `execution.context`, and `core.events.backpressure` without `core.events`. No document declares either as a dependency, so neither is enforced or advertised. Adding them would be new semantics, not a correction.

## Mixed-implementation composition (M6-Q2)

Mixed interoperability does not require completing every feature of a second provider. It requires the boundaries consumers actually cross to be exercised by two implementations over the public protocol. **Every session negotiates each profile with the provider that serves it:** Context and its features with the Context provider, Knowledge with the Knowledge provider, Evidence with the Evidence provider. No provider is required to support Execution because its caller is an executor.

### S-A: an independent execution kernel enforcing a required claim boundary

- **Role.** `conformance/thirdparty/minimal-executor` is an **independent execution consumer (kernel), not an Execution-profile provider**:
  - it serves no protocol operation and claims no `execution/1` conformance;
  - it owns its own dispatch and boundary logic;
  - it dispatches a deterministic fake execution.
- **Topology.**

  | Participant | Implementation | Serves | The kernel's session there |
  |---|---|---|---|
  | `knw` | reference | `knowledge/1` | none. The Context provider reads claims at `knw` under its own grant. |
  | `ctx` | reference | `context/1` with `context.claims`, and `evidence/1` for its own packets (CONTEXT §1) | a Context session (`context/1` with `context.required_before_start`, `context.advisory`, `context.claims`), and an Evidence session for packet bytes at the provider the packet reference names |
  | `evd` | reference | `evidence/1` | an Evidence session, in which it publishes its dispatch and check records |
  | `kernel` | third-party, contracts-only | nothing | client only, authenticating per U12 |

- **What the kernel does.** Test controls outside the production operations give it: a work list naming each work item's packet reference, obligation and fallback; its credentials and sockets; and the shared controlled clock.
  - **Evaluation.** At a work item's dispatch boundary it reads the bound packet revision's facts at `ctx` (`context.packet.inspect`), fetches the exact packet bytes and checks their digest, then decides from CONTEXT §14's read-time facts:
    - a required item in `invalidated_items` makes the binding stale;
    - a required item in `unverified_items`, or an unreadable provider, makes it unknown;
    - digest-mismatched bytes make it unsatisfied.
  - **Required work** is dispatched only when the binding is current.
  - **Advisory work** proceeds under its declared fallback, with the gap recorded.
  - **Records.** Each evaluation publishes a check record `check.<work>.<n>`, and each dispatch publishes `dispatch.<work>`, as sealed artifacts at `evd` through public `evidence/1` operations.
- **What the harness observes.** Only public queries at `evd` and `ctx`; it never reads a status computed by a reference executor.
- **Scenarios, each shown by check and dispatch records:**
  1. a valid required context allows dispatch;
  2. after the authority rejects the claim behind a required item, the required work is not dispatched (check state stale), while advisory work bound to the same packet is dispatched with its gap;
  3. with the Knowledge provider stopped, required work bound to a claim-carrying packet is not dispatched (check state unknown): unavailable knowledge never counts as valid;
  4. a change affecting only an advisory item does not stop unrelated required work;
  5. the same scenarios with the kernel's `ignores-required-boundary` mutant fail at the step expecting no dispatch.
- **Coverage claimed.** Consumer-side enforcement of CONTEXT §14 read-time facts at a required dispatch boundary, by a second implementation; packet fetch with digest check (CONTEXT §5, EVIDENCE §5); independent evidence publication.
- **Not claimed.**
  - `execution/1` provider conformance;
  - the EXECUTION §13.1/§13.3 wire shapes (`context.blocked`, queue reasons, checks in `execution.inspect`);
  - admission, capacity release and transition boundaries;
  - the Context and Knowledge providers themselves, which are the reference.

### S-B: an independent publisher feeding the reference Evidence and Verification providers

- **Role.** `conformance/thirdparty/minimal-publisher` is an independent Evidence publisher (client only).
- **Flow.**
  1. The publisher prepares, uploads and seals a verification contract artifact and a subject artifact at the reference provider, and computes each digest over the exact bytes it sent.
  2. It fetches the bytes back and checks both digests.
  3. The reference Verification provider, reached by the harness, records a receipt that names the contract by exact reference `{ provider, artifact, digest }`.
  4. The receipt is assessed against the subject's digest.
  5. Mutant: a publisher that uploads bytes differing from its declared digest is refused at seal (`content_digest_mismatch`), and the scenario fails.
- **Coverage claimed.** Evidence publication by a second implementation, consumed by the reference Verification provider through exact references and byte-integrity checks.

### S-C (optional)

Minimal Unix-socket serving in the independent provider, so that one composition runs with a second implementation in a serving role. Only if S-A and S-B land with time left.

## Carried-forward gaps: release disposition (M6-Q3, approved)

"Closed" means fixture and mutant evidence at the RC head. A closure that would change reference behavior, not merely guard it, first gets a compatibility assessment and, if it alters accepted semantics, an old-client fixture. Stricter validation is not additive merely because it falls within an accepted milestone's scope. The M5 contract-shape readings and the scripted-`unmet` resolution stay recorded in [M5-DIVERGENCES](M5-DIVERGENCES.md) and the specs. Nothing in M6 supersedes them silently.

**Required before release (the consequential four):**

| Gap | Why consequential | Closure |
|---|---|---|
| `decision.record` without `knowledge.read` on its claim (an unguarded authority path) | An authority check that only the reference enforces is exactly the class of divergence M2–M5 existed to prevent | Fixture step and mutant on the specified right check; no behavior change expected |
| Required-boundary enforcement checked on one implementation only (SCN-16, CMP-9 Execution side) | The claim boundary is 0.1's central safety promise to consumers | S-A |
| A job loses its evaluator before its first evaluation (HM5B-QUEUED-LOSS) | "Never a pass by absence" is Verification's core rule | Fixture and mutants: every property `indeterminate`, no `running`, an empty observation period, and the pinned version named |
| Exact `max_age_seconds` boundary | Boundary instants are where independent implementations silently diverge | Fixture at the exact instant on both sides, and a mutant that treats the boundary as stale |

**Accepted limitations (named in the release record):**
- no fairness bound among released executions;
- all Execution evidence is scripted; real adapters are PIO's gate;
- root is the only other OS user tested;
- capability evidence-source and cursor-past-head checks are reference-only;
- the independent provider serves stdio only (unless S-C lands);
- temporal reconstruction is deferred (M5-Q8);
- no signing or offline receipt verification (U2, Remote trust);
- Coordination is unsupported;
- Windows is unsupported (U4);
- the mixed-implementation remainder listed above.

**Deferred work (backlog, not blockers, kept with their impact):**
- **Evidence edge cases:**
  - `evidence.availability.changed`;
  - shrinking fetch limits;
  - a sealed but unavailable manifest child;
  - `released_holds` filtering;
  - rarer credential-locator forms.
- **Context edge cases:**
  - script `end`/`unmet` steps in Context's own flows;
  - `omit` naming an item;
  - `dirty_snapshot` and `environment_digest` in Context's own conditions;
  - cancel with no remaining subscriber;
  - job-event visibility;
  - shared jobs with different fallbacks;
  - corrections on advisory items;
  - `unverified_items` beyond `binding` and `evidence` items;
  - resolved conflicts left out of snapshots.
- **Revalidation timing edges:** advisory checks at dispatch; deadlines and inactivity due at release end.
- **Knowledge:**
  - the `conflict.resolve` step 7 order fixture (the decision path is guarded);
  - duplicate `condition_id`.
- **Verification:** rarer contract violations (unknown layer, non-boolean `required`, empty lists).
